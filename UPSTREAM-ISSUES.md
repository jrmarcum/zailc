# Issues found in upstream projects

zailc ports Fil-C's runtime and compiler pass to Zig and checks every piece against upstream
Fil-C and against zilc. While doing so we found the issues below in projects we depend on. Each
has a small, self-contained reproduction in this repository and was confirmed with the upstream
project alone, with no zailc code involved. They are listed for the maintainers' information.
zailc reproduces upstream's behaviour until a fix exists.

How each entry was established, and what zailc does about it, is recorded in
[`cmem/workarounds.md`](cmem/workarounds.md) under the entry number given.

---

## Fil-C

### 1. `landing_pad_impl` asserts `function_origin->can_catch` when a destructor writes a global (W-7)

Version: **Fil-C 0.686** prebuilt release (`filc-0.686-linux-x86_64`, commit `163fae5`). Linux
x86_64 (Ubuntu 26.04 under WSL2).

Reproduction: [`tests/upstream/filc-0.686-landing-pad-can-catch.cpp`](tests/upstream/filc-0.686-landing-pad-can-catch.cpp)

```cpp
static int n = 0;
struct G { ~G() { n++; } };
static void t() { G g; throw 1; }
int main() { try { t(); } catch (int) { std::printf("caught n=%d\n", n); } return 0; }
```

```sh
clang++ -O1 filc-0.686-landing-pad-can-catch.cpp -o repro && ./repro
```

```
filc panic: src/libpas/filc_runtime.c:7611: _Bool landing_pad_impl(filc_thread *, filc_ptr,
filc_ptr, filc_frame *, filc_frame *): assertion function_origin->can_catch failed.
```

Exit code 133. Expected: `caught n=1`, exit 0, which is what `-O0` prints.

- Happens at `-O1` and `-O2`, statically and dynamically linked.
- Does **not** happen when the destructor is empty, when it is `noinline`, or when it writes
  through a pointer to the caller's local instead of a global. It does happen at every recursion
  depth tried (0, 1, 3, 10) and through an intermediate frame.
- The runtime's own comments say this state cannot occur: `landing_pad_impl` notes *"If the frame
  didn't support catching, then we wouldn't have gotten here. Only frames that support unwinding
  call landing_pads"*, and `filc_runtime.h` documents that *"All functions generated by the
  compiler have can_catch == true for the function origin used at callsites."* So the frame being
  unwound carries a non-callsite origin when the exception passes through it. Our guess, which we
  have not verified, is that the pass gives the inlined destructor's store to the global an origin
  that becomes the frame's current origin at the throwing call.
