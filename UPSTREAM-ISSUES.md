# Issues found in upstream projects

zailc ports Fil-C's runtime and compiler pass to Zig and checks every piece against upstream
Fil-C and against zilc. While doing so we found the issues below in projects we depend on. Each
has a small, self-contained reproduction in this repository and was confirmed with the upstream
project alone, with no zailc code involved.

**This file is where zailc publishes them.** We don't file them in the upstream projects'
trackers; maintainers are welcome to reference and link to the entries here. Each entry is kept
current: corrected if our understanding changes, and marked fixed, with the version, once
upstream fixes it. zailc reproduces upstream's behaviour until a fix exists.

How each entry was established, and what zailc does about it, is recorded in
[`cmem/workarounds.md`](cmem/workarounds.md) under the entry number given.

---

## Fil-C

### 1. `landing_pad_impl` asserts `function_origin->can_catch` when a destructor writes a global (W-7)

Version: **Fil-C 0.686** prebuilt release (`filc-0.686-linux-x86_64`, commit `163fae5`). Linux
x86_64 (Ubuntu 26.04 under WSL2).

Reproduction: [`tests/upstream/filc-0.686-landing-pad-can-catch.cpp`](tests/upstream/filc-0.686-landing-pad-can-catch.cpp)

```cpp
static int n = 0;
struct G { ~G() { n++; } };
static void t() { G g; throw 1; }
int main() { try { t(); } catch (int) { std::printf("caught n=%d\n", n); } return 0; }
```

```sh
clang++ -O1 filc-0.686-landing-pad-can-catch.cpp -o repro && ./repro
```

```
filc panic: src/libpas/filc_runtime.c:7611: _Bool landing_pad_impl(filc_thread *, filc_ptr,
filc_ptr, filc_frame *, filc_frame *): assertion function_origin->can_catch failed.
```

Exit code 133. Expected: `caught n=1`, exit 0, which is what `-O0` prints.

- Happens at `-O1` and `-O2`, statically and dynamically linked.
- Does **not** happen when the destructor is empty, when it is `noinline`, or when it writes
  through a pointer to the caller's local instead of a global. It does happen at every recursion
  depth tried (0, 1, 3, 10) and through an intermediate frame.
- The runtime's own comments say this state cannot occur: `landing_pad_impl` notes *"If the frame
  didn't support catching, then we wouldn't have gotten here. Only frames that support unwinding
  call landing_pads"*, and `filc_runtime.h` documents that *"All functions generated by the
  compiler have can_catch == true for the function origin used at callsites."* So the frame being
  unwound carries a non-callsite origin when the exception passes through it.

**Cause (confirmed 2026-10-09).** Measured from the IR with `-mllvm -print-before-all
-print-after-all`:

1. FilPizlonator receives a correct block. After the early pipeline inlines `t` and `~G` into
   `main`, `lpad.i` starts with `landingpad`, followed by `load i32, ptr @_ZL1n`.
2. FilPizlonator emits the global's getter call (`call @pizlonated__ZL1n(ptr %0, ptr @filc_origin)`)
   and its access checks at the head of `lpad.i`, before the `filc_landing_pad` call that replaces
   `landingpad`. (LLVM requires `landingpad` to be the first non-PHI instruction of its block. The
   lowered form loses that ordering.)
3. On the global's first use, the getter's slow path calls
   `filc_global_initialization_start(my_thread, @filc_origin, ...)`, which sets
   `my_thread->top_frame->origin = passed_origin` (`filc_runtime.c:6546-6547`).
4. `@filc_origin`'s function origin has `can_catch = 0`. The callsite origins have `can_catch = 1`.
5. `filc_landing_pad` then calls `landing_pad_impl`, which asserts `can_catch` on that origin
   (`filc_runtime.c:7611`).

Confirmed by prediction: initialising `n` before the throw makes the panic disappear (the
reproduction's `-DWARM_GLOBAL_FIRST`: exit 0 at -O1 and -O2), while a fresh global first used in
the destructor still panics. We have not pinned the exact place in `FilPizlonator.cpp` that puts
the getter and checks at the block head. The access-check scheduler's backward hoisting to block
heads (`scheduleChecks`) is the likely one.

**Suggested fix:** in a landing-pad block, emit `filc_landing_pad` first, and never schedule
other code (getters, checks) above it.
